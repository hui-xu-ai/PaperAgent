## 1. 思考强度：事实、机制缺陷、建议（用户点名问的那条）

### 1.1 事实（可复核）
- 本会话 `set_thinking` 调用：① `high`（图片提取算法设计，动手前）；② `low`（算法完成后）；
  ③ `low`（收尾整理）。三次均返回"已确认：当前档位=X，对下一次模型请求生效"。
- 收尾前 `set_thinking(get)` → **`当前思考档位=high`**；`D:\DSH\.dsh\settings.yaml` 里
  `agent-default-model.reasoningEffort: **low**`。⇒ 运行态与配置默认值不一致，且与我最后一次设置不一致。
- 结论：**档位既没有被"我声称"地保持，也不等于配置默认值**，而是第三种状态 —— 无法从会话内自证。

### 1.2 机制缺陷（给创造模式的改法）
| # | 缺陷 | 建议 |
|---|---|---|
| T1 | `set` 的返回只说"对下一次请求生效"，**不说生效范围与当前活跃值**，也不说"最近被谁改过" | 返回里带：`生效范围(本会话/仅下一次)` + `当前活跃值` + `上次变更来源(agent/user/gui/default)` |
| T2 | 档位**不是会话级持久状态**：每轮从默认值/上次请求推导 ⇒ 出现"设 low、跑 high" | 档位存入 session 元数据（与 `sessionId` 绑定），只在 agent/user 显式变更时改 |
| T3 | 并行会话共享 `DSH_HOME`（`settings.yaml` mtime 13:03:54 与本会话无关地被写）⇒ 可能互相覆盖 | 会话级档位与全局默认分离；写入时带 session 标识，冲突时以"后写的会话"为准并记录 |
| T4 | **没有"该升档了"的外部触发器**：协议要求模型自省"这一步是不是架构步"，实测会漏（本会话全漏） | harness 侧信号：本步若生成/修改 ≥N 行的方案文档、schema/迁移、接口契约 → 主动提示或自动升档一次 |
| T5 | 档位变更**对用户不可见**（只在我回复里） | 写进会话事件流（用户的 UI 能看到"本步档位=high"），便于事后审计 |
| T6 | 降档没有校验闭环（我设了 low 但没在第 2 步复验） | `set` 之后自动附一句"下一步我会复验"，或 harness 在 N 步后自动 `get` 并写日志 |

### 1.3 模型侧的自省失效（诚实归因）
- 我把"架构工作"混在"连续执行流"里：先说方案（该升档）→ 立刻开写（执行，可降档）→ 又改 schema（该升档），
  **边界模糊时我默认落回低档**（省 token 的动机也在起作用）。
- 建议给 agent 一份**硬清单**（写进 `thinking-control`）：出现以下任一即升 high ——
  ① 修改 `docs/*` 里的规范/契约；② 改 schema/迁移/数据格式；③ 引入新接口/门面；④ 决定"保留 vs 删除"；
  ⑤ 写 `HANDOFF`/方案对比。**这五条本会话全中，一条没升。**

## 3. 工具调用：本会话三个真实摩擦（都影响步数）

1. **`restart-backend.ps1` 前台调用会挂住**：`pwsh -Command` 包装进程不退（多次 300s 超时、
   background job 长期 `running`），只能靠"端口 + `/api/health`"判断真实状态。
   ⇒ 建议：脚本自身 `Start-Process` 后立即 `exit`；harness 对"启动服务的命令"自动转后台并回端口探针。
2. **`pwsh` 引号地狱**：`python -c` 多行/中文引号失败多次（PW 无 heredoc），我只能
   `Set-Content work\_x.py` → 执行 → 删除，**本会话重复 10+ 次**。
   ⇒ 建议：harness 提供 `pyexec`（多行脚本或多行 stdin），直接消掉这类步数。
3. **`git add -A` 吞并行会话/历史未跟踪文件**：本会话差点把 `tools/cdp_eval.py` 提交进去。
   ⇒ 建议：`-A`/`.` 时提示"检测到 N 个非本会话产生的新文件"，或让 agent 只能按清单 add。

## 4. 子代理 / workflow / 多模型：为什么是 0，怎么改

- **诚实归因**：任务形态确实偏串行（取证→改→验证），我据此判断"并行收益低"。这个判断**部分成立**，
  但**至少三处该委派**：① 10 篇 PDF 抽看判"图是否夹正文"（便宜模型 + 结构化输出）；
  ② "哪些文件引用了旧路径"的全仓扫描（grep 类，可并行 4 路）；③ 迁移后逐表核对。
  我自己做了 ⇒ 主线步数与上下文都膨胀。
- **建议（给创造模式）**：
  1. 把判断表第 0 问变成**harness 强制**：单轮内出现 ≥3 个同类只读动作（如连续 read/grep）→ 提示
     "考虑 workflow 扇出 + 便宜模型"，并给出本次可扇出的清单；
  2. 提供**本项目的扇出模板**（批量文件体检 / 多篇产物核对 / 全仓引用扫描），降低启动摩擦；
  3. `workflow` 的返回里附"若主线自己做，预计多花 X 步 / Y token"——**量化收益**比"你应该并行"有效。

## 5. 记忆系统：本会话实测问题

- 做对的：HANDOFF 重写为 ≤80 行（69 行）、INDEX 索引化、专题落 `project/`、交接清单 `REMAINING`。
- 做错的：
  1. **入口超载**：`SHORT-TERM.md` 已 100KB+；我每批都往里写，导致"新会话读入口"本身就烧 token。
  2. **写入即入上下文**：每次记忆更新都是 write/edit 正文（与写代码同价）。
  3. **写入时机**：我"每批都写"，重复支付前缀成本；应**批次末尾/交接时一次性写**。
- 建议：① 记忆文件提供 **append 语义**（append-only + 索引重建），避免整文件改写；
  ② HANDOFF 硬限 ≤80 行（超了 harness 报警）；③ `SHORT-TERM` 超过 N KB 自动归档到 `project/`；
  ④ 明确"记忆写入 = 上下文成本"，写进协议。
